This doc details what emitters will generate for long-running operations.

## Resource create or replace

Long-running operation to create or replace a resource.

<ClientTabs>

```typespec
alias ResourceOperations = global.Azure.Core.ResourceOperations<NoConditionalRequests &
  NoRepeatableRequests &
  NoClientRequestId>;

/** Details about a user. */
@resource("users")
model User {
  /** The name of user. */
  @key
  @visibility(Lifecycle.Read)
  name: string;

  /** The role of user */
  role: string;
}

// Operation for polling the status of the LRO. SDK may exclude this operation from client.
@sharedRoute
op getOperationStatus is ResourceOperations.GetResourceOperationStatus<User, never>;

/** Create or replace the User. */
@pollingOperation(getOperationStatus)
op createOrReplace is ResourceOperations.LongRunningResourceCreateOrReplace<User>;
```

```python
def begin_create_or_replace(
    self, name: str, resource: Union[User, JSON, IO[bytes]], **kwargs: Any
) -> LROPoller[User]
```

```csharp
public virtual Operation<User> CreateOrReplace(WaitUntil waitUntil, string name, User resource, CancellationToken cancellationToken = default);
public virtual Task<Operation<User>> CreateOrReplaceAsync(WaitUntil waitUntil, string name, User resource, CancellationToken cancellationToken = default);
```

## Exposing status-monitor metadata

Use [`@lroStatusMetadata`](../../libraries/typespec-client-generator-core/reference/decorators.md#@Azure.ClientGenerator.Core.lroStatusMetadata) on an auxiliary property of a native Azure.Core LRO status-monitor model when generated SDKs should expose that value while polling. Typical values include progress, usage, job statistics, timestamps, and item-level diagnostics.

The generated poller or operation object exposes the latest value received from the status monitor, including values returned in the initial response and values available after a failed or canceled terminal response. A value can be absent until a response containing it arrives. Status metadata is refreshed after each poll and is not persisted in continuation tokens.

Apply the decorator only to auxiliary properties. The LRO status, logical result, structural error, polling location, and final location already control the LRO protocol and cannot also be status metadata. The decorator can be scoped to emitters, and multiple declarations on one property are allowed only when their scopes do not overlap.

This decorator describes metadata for language emitters; it does not change polling, terminal-state evaluation, error handling, or final-result extraction. It applies only to native Azure.Core LROs, not operations treated as long-running solely through the legacy `@markAsLro` decorator.

## Legacy LRO Decorators

:::caution
The decorators in this section are in the `Azure.ClientGenerator.Core.Legacy` namespace and should only be used for legacy compatibility scenarios.
:::

### Forcing an operation to be treated as long-running (`@markAsLro`)

If you have an operation that should be treated as a long-running operation but isn't recognized as one by default, you can force it using `@markAsLro`. The operation's return type must be a `Model`.

Use `@markAsLro` only for an operation that does not already have Azure.Core long-running-operation
metadata. Applying it to a native LRO has no effect and reports the `mark-as-lro-ineffective`
error. For an ordinary operation, the decorator creates only the client-side LRO shape; the
operation's response remains a normal output model rather than a native initial, polling, or final
envelope model.

```tsp
import "@azure-tools/typespec-client-generator-core";

using Azure.ClientGenerator.Core.Legacy;

model OperationResult {
  id: string;
  status: string;
}

@markAsLro
@post
op startProcessing(): OperationResult;
```
